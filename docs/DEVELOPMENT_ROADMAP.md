# LocalView 技术路线开发说明

> 版本：0.1.0
>
> 目标：指导 LocalView 从空项目发展为可发布的跨平台桌面应用
>
> 产品方向：面向 localhost 开发服务器的极简浏览器、服务管理器和预览调试工作台

## 1. 路线总览

LocalView 的开发应遵循“先验证技术底座，再完成核心闭环，最后扩展体验”的顺序。

```text
技术验证
   ↓
工程骨架
   ↓
本地项目管理
   ↓
开发服务器生命周期
   ↓
页面预览工作台
   ↓
跨平台稳定性
   ↓
高级调试和效率功能
   ↓
发布与持续维护
```

推荐拆成八个里程碑：

| 里程碑 | 目标 | 产出 |
|---|---|---|
| M0 | 验证关键技术风险 | 技术验证报告 |
| M1 | 建立可运行工程 | Tauri 基础应用 |
| M2 | 完成项目管理 | 项目配置和项目列表 |
| M3 | 完成服务管理 | 可启动、停止、监控 localhost 服务 |
| M4 | 完成预览工作台 | 内嵌页面、导航和日志 |
| M5 | 跨平台加固 | 主要系统可稳定运行 |
| M6 | Beta 体验完善 | 自动发现、工作区和调试增强 |
| M7 | 正式发布 | 安装包、更新机制和文档 |

## 2. 总体技术路线

### 2.1 第一原则：先做闭环

LocalView 的第一个真正可用版本应该完成下面的操作：

```text
选择项目目录
    ↓
配置启动命令
    ↓
启动开发服务器
    ↓
等待端口就绪
    ↓
在应用内预览
    ↓
查看日志
    ↓
停止整个进程树
```

在这个闭环稳定之前，不应优先开发主题商店、复杂标签页、账号系统或云同步。

### 2.2 第二原则：Rust 管系统，前端管体验

前端负责：

- 项目列表；
- 页面布局；
- 加载状态；
- 日志展示；
- 快捷键和交互；
- 用户偏好设置。

Rust 负责：

- 文件系统；
- 子进程；
- 端口探测；
- 配置保存；
- 系统窗口和托盘；
- 跨平台生命周期；
- 权限和参数校验。

不要把命令执行、路径访问或端口管理放到前端实现。前端只能调用明确的 Tauri Command。

### 2.3 第三原则：先抽象能力，再扩展界面

项目管理、进程管理、端口探测和日志事件应该先形成稳定的 Rust service，再接入 UI。这样后续增加自动扫描、工作区和多服务项目时，不需要重写核心逻辑。

## 3. M0：技术预研与风险验证

### 3.1 目标

M0 不追求漂亮界面，只验证 LocalView 最可能失败的技术点。

### 3.2 必须验证的内容

1. Tauri 2 能否正常创建窗口和加载前端；
2. 系统 WebView 能否稳定加载 Vite 页面；
3. HMR 和 WebSocket 是否正常；
4. Rust 能否启动 npm/pnpm/bun 开发服务器；
5. Rust 能否捕获 stdout/stderr；
6. Rust 能否停止完整的子进程树；
7. DevTools 是否能按目标平台打开；
8. localhost、127.0.0.1、本地 HTTPS 是否正常；
9. Windows、macOS、Linux 的路径和命令行为是否存在差异。

### 3.3 技术验证程序

建议建立一个临时实验目录，包含：

```text
experiments/
├── webview-test/
├── process-test/
├── port-probe-test/
└── devtools-test/
```

每个实验只回答一个问题，并记录：

- 操作系统；
- WebView 版本；
- 使用的包管理器；
- 执行命令；
- 预期结果；
- 实际结果；
- 发现的问题；
- 是否需要平台专用实现。

### 3.4 M0 验收标准

- 能打开一个真实的本地开发页面；
- HMR 至少在一个目标平台上工作；
- 能启动并停止一个 Node 开发服务器；
- 能获取服务日志；
- 明确系统 WebView 对 DevTools 的能力边界；
- 没有尚未评估的关键技术风险。

## 4. M1：建立工程骨架

### 4.1 目标

建立可编译、可调试、可测试的 Tauri 工程，并形成基础工程规范。

### 4.2 初始化技术栈

推荐组合：

```text
Tauri 2
Rust
React
TypeScript
Vite
Tokio
tracing
Vitest
Playwright
```

具体版本应在项目初始化时锁定，并使用 lockfile 保证开发者和 CI 使用一致依赖。

### 4.3 工程任务

- 初始化前端工程；
- 初始化 Tauri 工程；
- 配置开发模式和生产构建；
- 配置 Rust formatter 和 clippy；
- 配置 ESLint 和 Prettier；
- 建立环境变量约定；
- 建立基础错误处理；
- 建立 CI 的 lint、test 和 build 任务；
- 添加基础应用图标和窗口配置；
- 建立 `docs`、`src`、`src-tauri` 目录规范。

### 4.4 推荐工程约定

前端：

- TypeScript 开启严格模式；
- API 调用集中在 `src/lib/tauri.ts`；
- 页面组件不直接调用 `invoke`；
- 所有异步操作有 loading、success、error 状态；
- UI 状态和运行时服务状态分离。

Rust：

- Command 只负责参数接收和结果转换；
- 核心逻辑放在 service 模块；
- 错误统一转换为稳定错误码；
- 共享状态通过 `tauri::State` 注入；
- 不在 Command 内启动无法取消的后台任务。

### 4.5 M1 验收标准

- `dev` 模式可以启动桌面应用；
- 生产模式可以生成安装包或可运行构建产物；
- 前端和 Rust 均能通过静态检查；
- CI 能在干净环境执行基础检查；
- 应用关闭时不会残留测试进程。

## 5. M2：项目管理能力

### 5.1 目标

用户能够添加、编辑、删除和打开项目配置。

### 5.2 数据结构

核心项目模型：

```ts
type Project = {
  id: string;
  name: string;
  rootPath: string;
  workingDirectory?: string;
  startCommand: string;
  packageManager?: "npm" | "pnpm" | "yarn" | "bun" | "custom";
  url: string;
  port?: number;
  autoStart: boolean;
  createdAt: string;
  updatedAt: string;
  lastOpenedAt?: string;
};
```

### 5.3 实现顺序

1. 设计配置文件格式；
2. 实现配置加载；
3. 实现配置保存；
4. 实现版本号和迁移入口；
5. 实现目录选择；
6. 实现项目创建表单；
7. 实现项目编辑；
8. 实现项目删除；
9. 实现项目搜索和排序；
10. 实现最近打开记录。

### 5.4 配置存储路线

MVP 建议先使用 JSON：

- 结构简单；
- 易于调试；
- 不需要数据库迁移工具；
- 项目数量通常较少。

当出现以下需求时再迁移 SQLite：

- 大量日志需要查询；
- 多个工作区和多服务关系复杂；
- 需要历史运行记录；
- 需要按标签、状态和时间做复杂筛选。

### 5.5 数据安全要求

- 删除项目配置不删除项目文件；
- 保存使用临时文件加原子替换；
- 配置损坏时保留备份；
- 文件路径必须规范化；
- 不保存完整环境变量内容；
- 对配置版本做向前迁移。

### 5.6 M2 验收标准

- 可以添加一个真实项目；
- 重启应用后项目仍然存在；
- 无效目录、无效 URL 和空命令有明确提示；
- 删除项目不会影响项目目录；
- 配置写入失败时不会静默丢失数据。

## 6. M3：开发服务器生命周期

### 6.1 目标

实现 LocalView 最核心的原生能力：启动、观察、探测、停止和重启本地开发服务器。

### 6.2 模块拆分

```text
ProcessManager
├── start()
├── stop()
├── restart()
├── kill_process_tree()
├── read_stdout()
└── read_stderr()

PortProbe
├── tcp_probe()
├── http_probe()
├── wait_until_ready()
└── scan_local_ports()

RuntimeRegistry
├── project_id → process handle
├── project_id → runtime status
└── project_id → log buffer
```

### 6.3 启动流程

```text
接收 projectId
    ↓
加载并校验项目配置
    ↓
确认项目未运行
    ↓
检查工作目录
    ↓
构造程序和参数
    ↓
创建子进程
    ↓
注册 PID 和取消句柄
    ↓
异步读取输出
    ↓
轮询 TCP/HTTP
    ↓
发布 running 或 failed
```

启动命令需要尽量拆成“程序 + 参数”，例如：

```text
程序：pnpm
参数：run dev -- --host 127.0.0.1
```

对于确实需要 shell 特性的命令，必须明确标记为自定义命令，并在 UI 中提示用户风险。

### 6.4 日志设计

日志行模型：

```ts
type LogLine = {
  id: string;
  projectId: string;
  stream: "stdout" | "stderr" | "system";
  level: "info" | "warn" | "error";
  text: string;
  timestamp: string;
};
```

要求：

- 保存最近固定数量的日志；
- 前端使用虚拟列表，避免大量日志导致卡顿；
- stdout 和 stderr 分开标识；
- 不把日志无限写入磁盘；
- 页面关闭后仍可查看本次运行的最近日志；
- 日志中尽量屏蔽疑似 token 和 cookie。

### 6.5 停止进程树

不能只依靠一个 PID 假设所有子进程都会退出。开发服务器通常经过 shell、包管理器和实际运行时多层启动。

实现要求：

- 记录由 LocalView 创建的进程句柄；
- 优先进行温和终止；
- 等待有限时间；
- 必要时停止进程树；
- 不根据端口直接终止未知进程；
- 应用退出时清理仍由 LocalView 管理的服务；
- 在 Windows、macOS、Linux 分别进行验证。

### 6.6 M3 验收标准

- 能启动 npm、pnpm 或 bun 项目；
- 能显示实时日志；
- 能识别服务已就绪；
- 能识别端口占用；
- 能处理服务主动退出；
- 停止操作不会留下孤儿进程；
- 多项目同时运行时状态和日志不会串线。

## 7. M4：页面预览工作台

### 7.1 目标

把 LocalView 从服务启动器变为真正的 localhost 预览工具。

### 7.2 UI 实现顺序

1. 添加主布局；
2. 添加项目列表；
3. 添加预览区域；
4. 添加刷新、后退和前进；
5. 添加 URL 显示；
6. 添加服务启动、停止和重启按钮；
7. 添加日志抽屉；
8. 添加错误状态页；
9. 添加 DevTools 快捷键；
10. 添加窗口尺寸和布局持久化。

### 7.3 预览状态

预览页面至少要区分：

- 尚未启动；
- 正在等待开发服务器；
- 页面加载中；
- 页面已加载；
- 服务不可达；
- 页面返回错误；
- 服务已停止。

这些状态不能只显示一个通用的“加载失败”，否则用户无法判断是服务、端口还是页面本身的问题。

### 7.4 HMR 和 WebSocket 验证

必须用真实 Vite、Next.js 等项目验证：

- 文件修改后页面是否自动更新；
- WebSocket 是否能建立；
- 终端中的编译错误是否能在页面中反馈；
- 页面刷新后服务是否仍然可用；
- 预览容器是否阻止必要的 localhost 资源加载。

### 7.5 M4 验收标准

- 用户可以从项目列表启动并进入预览；
- 预览页面支持基本导航和刷新；
- HMR 正常工作或有明确限制说明；
- 服务停止后页面状态能及时更新；
- 日志和预览之间能快速切换；
- DevTools 在目标平台可用或有替代入口。

## 8. M5：跨平台稳定性与安全加固

### 8.1 目标

解决“本地开发环境差异”导致的稳定性问题，使应用可以进入 Beta 测试。

### 8.2 跨平台适配重点

Windows：

- 路径分隔符；
- PowerShell、cmd 和可执行文件查找；
- 进程树终止；
- 防火墙和本地 HTTPS；
- 安装目录和用户数据目录。

macOS：

- 应用签名和公证；
- 权限弹窗；
- shell 环境变量与终端环境差异；
- 应用关闭和窗口恢复。

Linux：

- 系统 WebView 依赖；
- 常见发行版差异；
- AppImage、deb 或其他发行格式；
- 文件管理器和默认浏览器调用。

### 8.3 安全加固清单

- 最小化 Tauri capability；
- 不开放任意路径读取；
- 不提供通用 shell Command；
- 用户自定义命令需要确认；
- URL 只允许 localhost 或用户明确输入；
- 外部链接显式交给系统浏览器；
- 敏感日志脱敏；
- 检查依赖安全公告；
- 发布包启用签名。

### 8.4 M5 验收标准

- 目标平台都能启动、关闭和重新打开应用；
- 目标平台都能运行至少一个测试项目；
- 应用关闭后没有残留由它启动的服务；
- 配置迁移和异常恢复有效；
- CI 能生成主要平台的构建产物；
- 基本安全测试没有高风险问题。

## 9. M6：Beta 功能路线

### 9.1 自动扫描本地端口

实现建议：

1. 只扫描常见开发端口范围和用户配置范围；
2. 先 TCP 探测，再执行轻量 HTTP 请求；
3. 根据响应标题、响应头和 HMR 特征进行提示；
4. 不自动添加项目，只提供发现结果；
5. 用户确认后再保存为项目。

端口扫描必须有范围、超时和停止机制，不能默认扫描所有端口或公网地址。

### 9.2 项目自动识别

可以按以下优先级识别：

1. `package.json` 的 scripts；
2. 包管理器 lockfile；
3. 框架配置文件；
4. 默认端口；
5. 用户手动确认。

自动识别只能生成建议配置，不能静默执行不明确的命令。

### 9.3 多服务项目

将单一 `Project` 扩展为：

```text
Workspace
└── Project
    ├── Service: frontend
    ├── Service: backend
    └── Service: docs
```

多服务功能需要先完成稳定的 RuntimeRegistry，否则会造成启动顺序、日志归属和停止逻辑混乱。

### 9.4 响应式预览

后续可提供：

- 自定义宽高；
- 常用移动设备尺寸；
- 横向和纵向切换；
- DPR 模拟；
- 多视口并列预览。

这部分属于 UI 增强，不应反过来影响服务管理核心。

## 10. M7：发布路线

### 10.1 发布前检查

- 核心用户流程手工验收；
- 安装、升级、卸载测试；
- 配置文件迁移测试；
- 进程清理测试；
- 空项目、无效项目和异常项目测试；
- 各平台 WebView 和 DevTools 测试；
- 包签名验证；
- 隐私说明和权限说明；
- 已知问题文档。

### 10.2 版本策略

建议使用 SemVer：

- `0.x`：快速迭代和验证产品方向；
- `1.0.0`：核心闭环稳定、可供日常使用；
- 次版本：新增兼容功能；
- 补丁版本：错误和安全修复。

每次发布需要包含：

- 版本号；
- 变更日志；
- 安装包；
- 校验和；
- 已知问题；
- 回滚或降级说明。

### 10.3 自动更新

自动更新应在基本发布流程稳定后再接入。需要考虑：

- 更新包签名；
- 下载失败重试；
- 用户可延后重启；
- 版本回滚；
- 更新期间正在运行的本地服务如何处理。

## 11. 迭代节奏与任务拆分

每个迭代周期建议只包含一个可验证目标。

### 迭代模板

```text
目标：本周期完成什么用户能力
范围：本周期包含哪些功能
不做：明确排除哪些内容
技术任务：前端、Rust、测试、文档
验收条件：用户如何判断完成
风险：可能阻塞交付的问题
复盘：实际结果和下一步调整
```

### 任务优先级

使用以下优先级：

- P0：阻塞核心闭环或存在数据/安全风险；
- P1：影响主要用户流程；
- P2：改善效率和稳定性；
- P3：视觉、扩展和实验性功能。

建议 P0 和 P1 任务完成后，再投入 P2、P3 功能。

### 12.1 每次提交

- ESLint；

- Rust clippy；

- Rust 单元测试。

### 12.2 合并请求

- 执行集成测试；
- 检查依赖锁文件；
- 生成测试报告；
- 检查文档是否同步。

### 12.3 发布标签

- 生成各平台安装包；
- 执行签名；
- 生成校验和；
- 发布变更日志；
- 上传制品；
- 保留构建元数据。

## 13. 质量指标

### 功能指标

- 新项目从添加到预览不超过几步；
- 服务启动成功率；
- 端口检测误报率；
- 服务停止后残留进程数量；
- 配置恢复成功率。

### 性能指标

- 冷启动时间；
- 内存占用；
- 日志高频输出时的 UI 响应；
- 端口探测耗时；
- 多项目并行运行时资源占用。

### 稳定性指标

- 应用崩溃率；
- 未处理错误数量；
- 进程清理失败率；
- 配置损坏率；
- 预览加载失败率。

## 14. 主要风险与应对

### 风险一：系统 WebView 能力不足

应对方式：在 M0 验证 HMR、WebSocket、DevTools 和本地 HTTPS。若高级调试能力不足，将调试功能拆成浏览器外部打开或独立调试窗口。

### 风险二：开发服务器进程无法完整停止

应对方式：建立平台专用进程测试，记录进程树，使用可取消任务和明确的终止策略，禁止按端口误杀未知程序。

### 风险三：不同包管理器行为不一致

应对方式：把 npm、pnpm、yarn、bun 适配做成独立的 command builder，并针对每一种工具编写集成测试。

### 风险四：自动识别项目误判

应对方式：自动识别只生成建议，必须允许用户编辑和确认。

### 风险五：功能范围膨胀

应对方式：以“本地服务启动—预览—停止”作为每个版本的核心验收线，所有新功能都要说明它如何改善这条主流程。

## 15. 推荐的首个开发顺序

如果现在立即开始编码，建议按下面顺序执行：

1. 初始化 Tauri 2 + React + TypeScript 项目；
2. 创建最小桌面窗口；
3. 加入一个静态的项目列表页面；
4. 实现 JSON 配置读写；
5. 实现添加项目表单；
6. 实现 Rust 启动子进程；
7. 实现 stdout/stderr 事件；
8. 实现 TCP/HTTP 就绪检测；
9. 实现服务停止和进程树清理；
10. 接入 localhost 预览页面；
11. 添加刷新、导航和 DevTools；
12. 加入错误状态和日志抽屉；
13. 进行 Windows、macOS、Linux 验证；
14. 冻结 MVP 功能并制作第一个 Beta 版本。

## 16. 首个版本完成定义

LocalView 的第一个 MVP 版本可以在满足以下条件后交付：

- 用户可以添加一个本地项目；
- 用户可以配置启动命令和 URL；
- 用户可以从应用中启动开发服务器；
- 应用可以显示实时服务日志；
- 应用可以检测 localhost 是否就绪；
- 应用可以在内置窗口中预览页面；
- 用户可以刷新和打开 DevTools；
- 用户可以停止服务；
- 应用退出后不会留下由它启动的孤儿进程；
- 配置不会因为普通异常退出而丢失；
- 至少一个主要桌面平台上的完整流程稳定可用。

## 17. 最终路线判断

LocalView 的技术路线不应该从“浏览器功能”开始，而应该从“开发服务生命周期”开始。进程管理、端口探测、日志事件和项目配置是底座；预览窗口、快捷键和布局是核心体验；自动发现、多服务和响应式预览是后续增长能力。

最合理的推进方式是：

```text
验证 WebView 与进程能力
    → 建立 Rust 核心
    → 完成项目和服务闭环
    → 接入预览体验
    → 做跨平台稳定性
    → 再扩展高级功能
```

按照这条路线，LocalView 可以保持工程复杂度可控，同时尽早产出一个真正能被开发者日常使用的产品。
